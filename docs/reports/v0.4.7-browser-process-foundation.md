## Shared command-invocation extraction

`src/core/resolveCommand.ts` gained an additive contract; existing
`resolveCommand()` behavior, signature, and result shape are untouched.

```ts
export type ResolvedCommandInvocation = {
  executable: string;
  args: string[];
  resolvedCommand: ResolvedCommand;
};

export function buildResolvedCommandInvocation(
  resolvedCommand: ResolvedCommand,
  args: readonly string[]
): ResolvedCommandInvocation;

export function resolveCommandInvocation(
  executable: string,
  args: readonly string[],
  options?: ResolveCommandOptions
): ResolvedCommandInvocation;
```

Argument assembly rules (one implementation, used by every new spawn site):

- `windows-cmd-shim` → `[...argsPrefix, resolvedPath, ...args]`
  (`cmd.exe /d /s /c call <shim> ...`).
- every other resolution kind, including `windows-powershell-shim` (whose
  `argsPrefix` already ends with `-File <resolvedPath>`) → `[...argsPrefix, ...args]`.
- `shell: true` is never introduced anywhere.

`runMeasuredCommand` no longer assembles shim arguments itself. Its
`resolveCommand: false` escape hatch now routes through
`buildResolvedCommandInvocation()` so even the bypass path shares the rule.

`src/securityValidation/commandRunner.ts` was intentionally left unchanged: it is
a different subsystem with its own pre-existing argument rule and
`allowPowerShellShim: false`, and changing it is outside this batch's scope.

## Process-termination extraction

`killProcessTree()` was removed from `runMeasuredCommand.ts` and replaced by
`src/core/processTree.ts`:

- `requestProcessTermination(pid)` — graceful `SIGTERM` request; never throws.
- `forceTerminateProcess(pid, { posixSignal? })` — Windows
  `taskkill /pid <pid> /T /F` with `shell: false`; other platforms
  `process.kill(pid, posixSignal ?? "SIGTERM")`.

The default `posixSignal` is `"SIGTERM"` precisely so the `runMeasuredCommand`
timeout path keeps its exact prior behavior. The managed-process forced-cleanup
escalation passes `"SIGKILL"`, which is safe there because it only runs after a
graceful grace period has elapsed.

Naming accuracy: the non-Windows branch signals **only the known process ID**. No
process-group or descendant traversal is performed on POSIX, and the file's
documentation states this explicitly rather than implying a POSIX tree kill.
`/T` does make the Windows branch a genuine tree termination.

## Managed-process implementation

`src/runtime/managedProcess.ts`, exported through `src/runtime/index.ts`.

- `startManagedProcess(spec)` validates a non-empty single-path-segment `id`, a
  non-empty `executable`, an existing directory `cwd`, and a usable `outDir`;
  creates `outDir` recursively; resolves the executable through
  `resolveCommandInvocation()`; and spawns with `shell: false` and
  `stdio: ["ignore", "pipe", "pipe"]`.
- Environment is merged as `{ ...process.env, ...spec.env }`.
- Logs stream continuously to `<outDir>/<id>.stdout.txt` and
  `<outDir>/<id>.stderr.txt` via `createWriteStream` + per-chunk writes, so a
  long-lived process's log is readable while it runs. Nothing is printed to the
  user's terminal by this owner.
- In-memory retention is bounded: `MANAGED_PROCESS_CAPTURE_LIMIT_BYTES = 256 * 1024`
  per stream, exposed through the additive read-only `readRecentOutput()`
  diagnostic accessor. The on-disk logs remain complete and untruncated.
- `waitForExit()` resolves once and hands every caller the identical normalized
  `{ exitCode, signal, error? }` object.
- `stop({ gracePeriodMs })` (default `1500`) is idempotent: `already-exited` when
  the child is already gone, `stopped` when it exits within the grace period,
  `forced` when escalation was required. Concurrent calls share one in-flight
  operation.
- No global mutable process registry exists; a handle is the only reference. The
  owner never reuses an already-running process and never infers `outDir` from
  `cwd`, so package root, workspace, inspected target, and log output stay
  distinct.
- `child.on("error")` is attached before any early return, and both log streams
  have error handlers, so no `error`/`exit`/`close` event escapes unhandled.

Error pattern: start-time problems throw `ManagedProcessStartError` (there is no
handle to return); runtime states a caller must handle are returned as structured
results.

## Readiness policy

`waitForReadiness(probe)` accepts only `kind: "http"`.

- Allowed hosts: `localhost`, `127.0.0.1`, `::1` (including the `[::1]` form
  produced by URL parsing). Any other host is rejected before a request is made.
- Allowed protocols: `http:`, `https:`.
- Defaults: `intervalMs = 100`, `requestTimeoutMs = min(1000, remaining budget)`,
  accepted status range `200..399`.
- `redirect: "manual"` keeps a 3xx observable as a 3xx rather than following it,
  so a redirecting local server satisfies the default range (verified against
  this Node runtime's `fetch`).
- Connection refusal, socket failure, and per-attempt aborts are retried until
  the overall budget expires.
- Statuses: `ready`, `timeout` (budget expired), `process-exited` (child died
  before readiness), `probe-failed` (invalid probe configuration; `attempts = 0`).
- Elapsed time uses `Date.now()` deltas; `attempts` and `elapsedMs` are always
  populated. No dependency was added — Node's built-in `fetch` and
  `AbortSignal.timeout` are used.

## Remaining risks

- POSIX forced cleanup signals only the known PID. A managed process that spawns
  its own grandchildren could leave them running on Linux/macOS. This matches the
  pre-existing `runMeasuredCommand` behavior and is documented rather than
  silently implied to be a tree kill; a real process-group strategy would change
  the spawn contract and belongs to a later batch if a Batch 2 target needs it.
- The IPv6 loopback readiness test returns early on hosts without a usable `::1`
  listener. The loopback address policy is still fully proven by the `localhost`
  and `127.0.0.1` cases and by the external-host rejection case.
- `startManagedProcess` throws for an unavailable command rather than returning a
  structured unavailable result. If Batch 2 needs a non-throwing start outcome, a
  structured start result can be added additively.
- `src/securityValidation/commandRunner.ts` still assembles its own argument
  array. It was out of scope here; converging it on `resolveCommandInvocation()`
  is a candidate for a later bounded change.
