## Playwright video configuration

The persistent context is created with `viewport` = the scenario viewport and
`recordVideo: { dir: <runRoot>/temporary/video, size: <scenario viewport> }`. No
video size is invented. `tutorial validate` and `captureReportScreenshot` never
request recording — only tutorial execution does.

## Canonical artifact paths

| Artifact | Path (relative to runRoot) |
| --- | --- |
| Video | `artifacts/tutorial.webm` |
| Subtitles | `artifacts/tutorial.srt`, `artifacts/tutorial.vtt` |
| Markdown | `artifacts/tutorial.md` |
| Manifest | `artifacts/tutorial-manifest.json` |
| Step screenshots | `screenshots/<screenshot-id>.png` |
| Raw recording (temporary) | `temporary/video/` |

Screenshot paths come only from the validated stable-id contract via
`buildScreenshotPath()`, which additionally enforces containment under
`screenshotsRoot`. No artifact path is ever accepted from scenario JSON.

## Video finalization behavior

Lifecycle: create recording context → create the one page → capture
`page.video()` → run steps → close page and context (Playwright finalizes the
recording only on page close) → `video.saveAs(artifacts/tutorial.webm)` → verify
the file exists, is a regular file and is non-empty → remove raw `.webm` files
from `temporary/video/` → close the browser → stop managed processes.

`video-finalization-failed` is returned when recording started and execution
otherwise passed but the canonical WebM could not be saved, is missing, or is
zero bytes. On failure the raw recording is deliberately retained and its
location is reported as a warning, because it is the only diagnostic material
left. WebM only: no FFmpeg, no MP4, no re-encoding, no container renaming.

## Partial video on failed tutorials

Video finalization runs after step execution regardless of outcome, so a failed
tutorial still produces a usable recording. Run status and video artifact status
are independent facts in both `TutorialRunResultV1.artifacts` and the manifest: a
failed tutorial with a valid WebM is still a failed tutorial, and a video
problem never overwrites an action/assertion failure (it is recorded in
`warnings` instead).

## Cursor implementation

One tutorial-owned container (`__my_dev_kit_lab_tutorial_visuals__`) holds the
cursor (`__my_dev_kit_lab_tutorial_cursor__`) and click ripple. Everything uses
`pointer-events: none`, so nothing can intercept application input; Playwright
still performs every real interaction and the cursor is presentation only.

Movement is a fixed `transform 250ms linear` transition
(`CURSOR_MOVE_DURATION_MS = 250`) — no physics, no randomized easing, no
machine-dependent timing. The cursor moves to the bounding-box center before
`click`, `fill`, `press` and `hover`, to the source before `drag` and to the drop
target after the real drag completes, and is deliberately not moved for `goto` or
`wait-for`. A null bounding box records a visual warning and the real action
still runs.

**Found by the real browser:** a `goto` replaces the document and destroys the
injected DOM. Installation is idempotent and is now re-run at the start of every
step and again after a successful navigation, so the cursor survives without
tracking navigation events.

## Click feedback implementation

A click ripple is appended at the cursor point after the real click, removes
itself after `CLICK_FEEDBACK_DURATION_MS = 300`, replaces any stale ripple rather
than accumulating, uses `pointer-events: none`, and does not affect application
layout. The step waits only that 300 ms so the ripple is visible in the
recording.

## Highlight implementation

A fixed-position outline plus a light wash derived from the target's bounding
box, drawn as a sibling inside the tutorial container. The target element's own
DOM, class list and styles are never touched, and the overlay is never consulted
by assertions. Padding keeps the target's content readable.

## Callout implementation

Text comes verbatim from `step.callout.text`. With a locator, the callout is
positioned relative to that element's bounding box; without one it uses a
deterministic bottom-center viewport position. `pointer-events: none` throughout.

`auto` placement uses this exact documented branch order, with no search and no
randomness:

1. target center left of the viewport's left third → `right`
2. target center right of the viewport's right third → `left`
3. horizontally centered and in the upper half → `bottom`
4. otherwise → `top`

## Screenshot timing

Capture point, per step: **after the action, after all assertions, after the
highlight/callout have been applied, and after `pauseAfterMs`** — so a screenshot
always shows the final intended state of its step. Captures use the already-open
tutorial page (`page.screenshot`); `captureReportScreenshot()` is never called and
no second browser or navigation occurs. `fullPage` defaults to `false`.

A step whose action failed records the screenshot as `skipped` with the reason
rather than fabricating an image. An existing canonical screenshot path is an
artifact error — never a silent overwrite and never a random suffix.

## Tutorial timeline

`TutorialStepResultV1` gained `timelineStartMs` / `timelineEndMs`, measured from
a monotonic clock started with the recording session (injectable for tests). The
existing `startedAt` / `endedAt` / `durationMs` wall-clock fields are preserved as
operational evidence. Values are monotonic across steps, satisfy
`timelineEndMs >= timelineStartMs >= 0`, and include `pauseBeforeMs`, action time,
assertion time and `pauseAfterMs` because all of those are inside the recording.
Not-run steps carry no timeline.

## SRT / VTT generation

One cue per executed step that has narration and a recorded timeline; not-run
steps produce no cue. Narration is `TutorialStepV1.narration` verbatim — never
rewritten, summarized or duplicated into a second source. A cue shorter than
`MIN_SUBTITLE_DURATION_MS = 500` is extended for display only, capped at the next
cue's start so cues never overlap or invert; step timing evidence is unchanged.

SRT: numbering from `1`, `HH:MM:SS,mmm`, blank-line separated, no styling markup.
VTT: `WEBVTT` header, `HH:MM:SS.mmm`, no cue settings or metadata. Both use
deterministic LF endings and a single trailing newline, and consume structured
results only — never `tutorial.md` or the manifest.

## Markdown generation

`# <title>`, the optional description, then `## Step N: <step id>` with the
verbatim narration for each executed step in scenario order. A successful
screenshot is linked as `![<step id>](../screenshots/<screenshot-id>.png)` using
POSIX separators; a failed or absent screenshot produces no image. A failed
executed step is plainly marked as failed with its run error and no invented
troubleshooting advice. Not-run steps are omitted entirely. No absolute paths.

## Tutorial manifest schema

`TUTORIAL_MANIFEST_SCHEMA_VERSION = "1.0.0"`, its own schema — `GalleryManifest`
is not reused. Contains scenario, target, run, environment, per-step records
(status, verbatim narration, timeline, action, assertions, screenshot record,
highlight/callout requested, error), the artifact list, warnings and cleanup
errors. Step order is scenario order and assertion order is execution order.
Written as `JSON.stringify(value, null, 2)` plus one trailing newline.

Every stored path is run-root-relative with POSIX separators
(`artifacts/tutorial.webm`, `screenshots/app-open.png`,
`logs/processes/viewer.stdout.txt`); the smoke run confirmed zero absolute or
backslash paths. Content is built from structured results — directories are
scanned only to verify size/existence of files this run wrote.

## Artifact status behavior and run status additions

`TutorialRunStatus` gained `video-finalization-failed` and `artifact-failed`; all
Prompt 2 statuses are preserved and unrenamed. `TutorialRunResultV1` gained an
additive `artifacts` summary (video, srt, vtt, markdown, manifest, screenshots)
so a CLI consumer never has to parse the manifest to learn whether artifact
generation failed.

Generation order: finalize WebM → subtitles → Markdown → stop processes → build
manifest → write manifest → final status.

Final-status precedence for an otherwise-passing run, most specific first:
`video-finalization-failed` → `artifact-failed` → `cleanup-failed`. A real
execution failure is never replaced by an artifact failure; artifact problems are
appended to `warnings` instead.

**Gap found and fixed during implementation:** failures occurring after the run
directory exists (prepare, process start, readiness, browser unavailable/failed)
originally returned before any manifest was written, contradicting the
requirement that a manifest be attempted whenever run identity and paths exist.
Those paths now write a manifest reporting the real failure with every tutorial
artifact marked `skipped` — nothing is claimed to exist, and the early failure is
not reclassified as a video problem.

## Remaining risks

- The real-browser suite is verified on Windows only. Playwright's recording and
  bounding-box behavior are cross-platform, but Linux/macOS Chromium has not been
  exercised here; Prompt 4 owns CI browser provisioning.
- Cursor re-installation is keyed to step boundaries and successful `goto`. An
  in-page navigation triggered by a click (not present in the fixture) would lose
  the overlay until the next step's re-install.
- `tests/integration/tutorialRealBrowser.spec.ts` skips when Chromium is absent.
  That keeps the default suite deterministic but means the real-browser proof is
  environment-dependent until Prompt 4 sets the CI policy.
- Screenshot and video content are verified structurally (PNG signature,
  dimensions, WebM magic bytes, non-zero size) and by live DOM assertions during
  execution. Subjective visual quality is not machine-verified; no OCR or
  image-recognition dependency was added.
- Prompt 1/2 residual risks are unchanged.
