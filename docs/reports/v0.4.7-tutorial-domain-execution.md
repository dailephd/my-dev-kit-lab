## Schema versions

`TUTORIAL_SCHEMA_VERSION = "1.0.0"` and
`TARGET_CONTRACT_SCHEMA_VERSION = "1.0.0"`. Both validators accept `1.0.0` and
nothing else: a missing, non-string, malformed, different-major or
different-minor version is rejected, and nothing is auto-upgraded or
reinterpreted. `TutorialRunResultV1` carries its own `schemaVersion: "1.0.0"`.

## Scenario schema

`TutorialScenarioV1` = `schemaVersion`, `id`, `title`, optional `description`,
`targetId`, `browser.viewport {width, height}`, and `steps[]`. A step carries
`id`, `narration`, optional `pauseBeforeMs`/`pauseAfterMs`, optional `action`,
`highlight`, `callout`, `screenshot`, and `assertions[]`.

Validation is strict and closed:

- ids (scenario, target, step, screenshot, process) must match
  `^[a-z0-9][a-z0-9._-]*$`;
- non-empty title; non-empty narration after trimming; at least one step and at
  most `MAX_TUTORIAL_STEPS` (500);
- unique step ids and unique screenshot ids;
- pauses are finite non-negative integers no greater than `MAX_STEP_PAUSE_MS`
  (60000); timeouts are finite positive integers (zero, negative, `NaN`,
  `Infinity` and non-integers all fail);
- viewport width 320–3840 and height 240–2160;
- unknown action, assertion and locator kinds fail, and **unknown object fields
  fail** rather than being silently ignored — this is what stops a scenario from
  carrying a `script`/`shell`/`eval` field that a permissive validator would drop.

`highlight`, `callout` and `screenshot` are fully validated here but produce no
visual output in this batch; only the "requested" flags are recorded.

## Target contract schema

`TutorialTargetContractV1` = `schemaVersion`, `id`, `prepare`, `processes[]`,
`applicationUrl`. `prepare` is `{executable, args?, env?}`. A process is
`{id, executable, args?, cwd?, env?, readiness}` where `cwd` is `contract-root`
(default) or `target-root`, and `readiness` is the Prompt 1
`LocalHttpReadinessProbe`.

Requirements enforced: a prepare command, at least one process, unique process
ids, non-empty executables, string-only args, string-only env keys and values,
a valid `contract-root`/`target-root` cwd, and an `http:`/`https:` loopback
`applicationUrl` and readiness url. `shell`, `commandString`, `script`,
`javascript`, `eval` and `command` are rejected by name with an explanatory
message wherever they appear, in addition to being excluded by the closed key
lists.

The only placeholder is `{{targetRoot}}`, permitted in `prepare.args`,
`prepare.env` values, `process.args` and `process.env` values. Any other
`{{...}}` occurrence is a validation error; substitution is a literal string
replacement, not a template evaluator.

## Target identity

`scenario.targetId` must equal `targetContract.id`. The check runs before the run
directory is created, so a mismatch returns `target-mismatch` having run no
prepare command, started no process and launched no browser — proven by a test
that asserts the output directory does not exist afterwards.

## Locator, action and assertion types

Locators (4): `role`, `text`, `css`, `test-id`.

Actions (7): `goto`, `click`, `fill`, `press`, `hover`, `drag`, `wait-for`.

Assertions (8): `element-visible`, `text-equals`, `text-contains`,
`url-path-equals`, `attribute-equals`, `http-json-equals`, `json-file-equals`,
`file-exists`.

`resolveTutorialLocator(page, locator)` in `src/tutorial/tutorialLocators.ts` is
the single mapping site: `role` → `getByRole`, `text` → `getByText`, `css` →
`locator`, `test-id` → `getByTestId`. Actions and assertions both call it, and a
test proves all three paths produce byte-identical page calls. `drag` resolves
both ends through it. No tutorial-level retry loop exists — Playwright's
per-call timeout is the only waiting mechanism, defaulting to
`DEFAULT_TUTORIAL_ACTION_TIMEOUT_MS` / `DEFAULT_TUTORIAL_ASSERTION_TIMEOUT_MS`
(5000 each).

## JSON Pointer behavior

RFC 6901 only. `""` addresses the whole document; `/field`, `/parent/child` and
`/array/0` address members; `~1` decodes to `/` and `~0` to `~`, decoded in that
order so an encoded separator is not re-interpreted. A malformed escape (`~2`) is
rejected both at validation time and at resolution time. A missing property, an
out-of-range or non-numeric array index, and a segment applied to a non-object
are all assertion failures with a specific message. No JSONPath, no dot notation,
no expression evaluation.

## Same-origin and containment boundaries

- **Navigation:** `goto.path` must begin with `/` and must not be
  protocol-relative. It resolves only against `applicationUrl`, and the resolved
  URL's protocol, hostname and port must match exactly. Enforced twice — at
  validation time and again at navigation time.
- **HTTP assertions:** identical rule via `resolveAssertionRequestUrl`. A non-2xx
  response, unreadable body, invalid JSON, unresolvable pointer, non-scalar value
  or scalar mismatch are all ordinary assertion failures, never thrown
  exceptions. Requests use a bounded `AbortSignal.timeout`.
- **Application origin:** must be loopback (`localhost`, `127.0.0.1`, `::1`),
  which is what makes the same-origin rules meaningful.
- **File assertions:** `json-file-equals.path` and `file-exists.path` resolve
  beneath `TutorialRunPaths.targetRoot` using path-semantics containment
  (`resolveWithinRoot`), never string-prefix matching, so a sibling such as
  `<root>-other` is correctly outside. Empty, absolute (even when pointing
  inside), traversal and Windows drive-qualified paths are all rejected.
  `file-exists` requires a regular file; a directory does not satisfy it.

## Output path model

```
TutorialRunPaths = { runRoot, targetRoot, artifactsRoot, screenshotsRoot, logsRoot, temporaryRoot }
```

Default layout: `<workspaceRoot>/tutorials/<scenario-id>/<run-id>/`, with
`target/`, `artifacts/`, `screenshots/`, `logs/` and `temporary/` beneath it. All
five are created up front so the layout is stable even for a run that fails
early. Batch 2 writes only into `target/` (via prepare) and `logs/`.

`--out` semantics: an absolute value is used exactly as given and is deliberately
**not** relocated beneath the workspace; a relative value resolves against
`LabExecutionContext.invocationCwd`. Run ids come from
`generateTutorialRunId()` (compact UTC timestamp plus a UUID fragment), are a
safe single path segment matching the id pattern, and are injectable for tests.
There is no `--run-id` flag.

## Prepare behavior

Prepare runs through the existing `runMeasuredCommand` with
`cwd = contractRoot`, logs under `<runRoot>/logs/prepare/`, and
`{{targetRoot}}` expanded in args and env. A nonzero exit returns
`prepare-failed` with the log paths in the message. A zero exit that did not
create `<runRoot>/target/` as a directory also returns `prepare-failed` — the
trusted prepare command is the only thing allowed to populate `targetRoot`, so
its success alone is not accepted as proof. No managed process starts after a
prepare failure.

### Bounded Prompt 1 extension: structured command input

`runMeasuredCommand` gained a second, mutually exclusive input form:
`{executable, args}` alongside the original `{commandString}`. This was necessary
to reuse the owner rather than work around it. `quoteCommandPart()` escapes
backslashes but `parseCommandString()` does not unescape them, so a Windows
executable path round-tripped through a command string comes back with doubled
separators — verified directly against the existing helpers before making the
change. A caller that already holds a discrete executable and argument array now
passes them through untouched; `commandString` in the result is produced by
`serializeCommand()` for the telemetry record and is never parsed back. The union
type keeps compile-time exclusivity, and every pre-existing caller and test is
unaffected.

## Managed process reuse

Process startup iterates `targetContract.processes` in declared order and calls
the existing `startManagedProcess()` and `handle.waitForReadiness()` from Prompt
1. No second resolver, termination helper, readiness implementation or process
subsystem was created. Logs land under `<runRoot>/logs/processes/`.

- A start failure returns `process-start-failed`;
- readiness `timeout`, `process-exited` or `probe-failed` returns
  `readiness-failed`, with a message naming the process, the url and which of the
  three occurred;
- either failure stops all already-started processes in reverse startup order and
  does not launch the browser.

## Browser session lifecycle

The browser launches only after every declared process is ready, through the
Prompt 1 `launchChromium()` owner. `unavailable` (module missing or Chromium
binary missing) maps to `browser-unavailable`; an unexpected launch failure maps
to `browser-failed`.

After a successful launch the run creates exactly **one** context (with
`scenario.browser.viewport`), exactly **one** page, and drives every step against
that same page — proven by tests asserting `contextsCreated() === 1`,
`pagesCreated() === 1`, and shared page state across steps.
`captureReportScreenshot()` is never called from tutorial execution.

## Step failure semantics

Per step: record start → `pauseBeforeMs` → action (if any) → assertions (only if
the action phase completed) → `pauseAfterMs` (only if the action phase completed)
→ record end and duration.

- An action failure marks the step failed and **skips that step's assertions**.
- Assertion failures do **not** short-circuit each other: every assertion in the
  current step runs and is recorded before the step is finalized.
- Either failure stops later steps, which are reported with status `not-run` —
  never omitted, never reported as passed.
- A narration-only step is valid and passes.

## Cleanup semantics

Cleanup always runs, in order: page close (when the runtime exposes one), context
close, browser close, then managed processes in reverse startup order. Browser
resources are released before the processes they were talking to — asserted by a
test on the recorded event order.

Cleanup errors are collected into `cleanupErrors` and **never** replace a primary
failure: a run that failed at a step still reports `step-failed` with the cleanup
error recorded separately. A run that would otherwise have passed but failed
cleanup reports `cleanup-failed`, because reporting `passed` would misstate a
leaked resource.

## CLI routes

- `my-dev-kit-lab tutorial --help`
- `my-dev-kit-lab tutorial validate --scenario <path> [--target-contract <path>] [--json]`
- `my-dev-kit-lab tutorial run --scenario <path> --target-contract <path> [--out <dir>] [--json]`

`src/cli/runLabCli.ts` gained only a `tutorial` family dispatcher matching the
existing family pattern; no tutorial logic lives in the router. Both command
owners are thin adapters.

`tutorial validate` is read-only: no run directory, no prepare, no process, no
browser, no report file. Exit codes: `0` valid, `1` content validation failed,
`2` usage error. `tutorial run` exit codes: `0` only when the run status is
`passed`, `1` for every other status, `2` for usage errors. `--json` output is
deterministic and parseable. Human output names scenario id, target id, run id,
run root, status, step counts, the failed step and the primary error, and never
dumps child-process logs.

The run command owner exposes a narrow injection seam (`runTutorialImpl`,
`launchBrowser`, `generateRunId`) so CLI tests exercise routing, parsing, output
and exit codes without a real browser or target. The CLI was not redesigned
around dependency injection.

## Remaining risks

- The `PlaywrightLikeTutorialPage` locator surface is structural and unverified
  against a real Chromium in this batch. Prompt 3 owns real-browser integration
  and will be the first place a genuine Playwright page exercises these calls.
- `text-equals` compares raw `textContent` with no trimming, per the planner's
  "exact equality". Scenarios against whitespace-heavy markup may need
  `text-contains`.
- `PlaywrightLikeBrowserContext.newPage()` now returns the tutorial page type.
  Nothing implemented that interface before this batch, but it is a narrowing for
  any future external implementor.
- Prompt 1's residual risks are unchanged and were not expanded on here: POSIX
  forced cleanup signals only the known PID; IPv6 readiness depends on host `::1`
  support; `startManagedProcess` throws for an unavailable executable (Batch 2
  catches this and maps it to `process-start-failed`); `docs/reports/` needs
  `git add -f`.
