READ THIS FIRST — MANDATORY AGENT INTAKE
----------------------------------------
1. Before inspecting or editing a project task, read this complete manifest.txt AND whichever existing local agent-instruction files apply: agents.txt, claude.txt, AGENTS.md, CLAUDE.md, or nested agent files. Do not assume a filename is automatically loaded by your coding-agent platform. The invocation/bootstrap instructions must explicitly tell the agent to read this file.
2. Also consult docs/ARCHITECTURE.md for detailed subsystem boundaries, docs/CURRENT_STATE.md for operational state, docs/ROADMAP.md for fixed planned scope, docs/DOCUMENTATION_PRESERVATION_POLICY.md for retention rules, and the actual code/tests/config relevant to the task. Read only what is relevant after this intake.
3. Take inventory: git branch --show-current; git rev-parse HEAD; git status --short --untracked-files=all; inspect .gitignore, .npmignore, package.json files, and the relevant owner/tests before edits.
4. State the existing OWNER DIRECTORY, OWNER MODULE, CLOSEST TEST LOCATION, REQUIRED OUTPUT LOCATION, and MINIMAL EDIT SET. If ownership is uncertain, inspect imports, registries, tests, and callers; use bounded my-dev-kit search/lookup/source when available. Never invent an owner from a feature name.
5. Extend the existing implementation owner. Never add a parallel runner, CLI router, report writer, validation system, shared utility folder, experiment registry, or test framework merely because a new task is being implemented.
6. No new top-level directory, unrelated cleanup, relocation, deletion, archive, unrequested file, or version-scope change is authorized by reading this manifest. Propose structural changes with evidence and a migration plan; implement only under an explicit task authorization.
7. Preserve local/user/ignored content. Do not run git clean/reset/restore/stash/rebase, destructive moves, force-push, or blanket git add. Do not commit/push, release, tag, or publish unless explicitly authorized.
8. Run work silently on Windows: no visible shell, Explorer, browser, editor, GUI, or extra console windows. Browser tests, when required, are headless.
9. Before declaring completion, show the files created/moved/deleted, where they belong in this manifest, why existing owners were reused, focused tests, docs/structure checks, git diff --check, and any unresolved placement issue.
10. If an agent file conflicts with this manifest, source evidence, or explicit user scope, do not silently pick the convenient interpretation. Respect the explicit task and protected public/private boundaries; report the conflict.

- Security scanners / Gradle / browser/network external operations must preserve each subsystem's opt-in and non-destructive behavior.

MANDATORY FILE-PLACEMENT DECISION BEFORE EACH CHANGE
----------------------------------------------------
A. Is this end-user capability logic? Place in existing src/<owner>/, not scripts/, docs/, tests/, benchmarks/.
B. Is this installed CLI routing/help? src/cli/. Is it a reusable CLI command? src/commands/. Is it an npm script entrypoint? scripts/ only, delegating to src/commands/.
C. Is this a NEW experiment family? Extend src/experiments/plugins/ through the existing registry and generic runner, ONLY if the approved version explicitly adds the family. Core experiment runtime changes belong in src/experiments/.
D. Is this shared scientific/evaluation logic? src/evaluation/<existing owner>/; do not bury it in a report renderer or clone it into another plugin.
E. Is this a security validation check? src/securityValidation/<specific existing category>/; Android-specific static analyzer? src/mobile/android/advancedSecurity/<specific category>/; generic audit? src/audits/. Use src/audits/security/ ONLY for conversion and summary.
F. Is this a report? Shared experiment report src/report/experiments/; standalone audit report src/audits/report/; standalone security report src/securityValidation/report/; Android report src/mobile/android/report/. Distinguish render logic from experimental computation.
G. Is this a user-facing document? Update the existing docs/<responsibility>.md rather than creating docs/<feature-name>-notes.md. Historical release state belongs in CHANGELOG.md or a specifically authorized archival record.
H. Is this an experiment answer key/fixed corpus? benchmarks/contracts/ and benchmarks/projects/. Is this a fake target for automated regression? tests/fixtures/. Never mix these simply because both look like samples.
I. Is this a test? Mirror the existing production owner in tests/<matching path>; prefer modifying established tests. Test fixtures go under the established tests/fixtures/<domain>/.
